## Endpoint inventory

| Method | Path | Summary | Params | Response schema ref | Auth required |
|--------|------|---------|--------|----------------------|----------------|
| GET | /ping | Health check — confirms the API is reachable | none | plain string body `Created` (no JSON schema) | None |
| POST | /auth | Exchange username/password for an auth token | body: `username`, `password` | AuthToken (`{"token": string}`) | None |
| GET | /booking | List booking ids, optionally filtered | query (all optional): `firstname`, `lastname`, `checkin`, `checkout` | BookingIdList (array of `{"bookingid": int}`) | None |
| GET | /booking/{id} | Fetch one full booking record | path: `id` | Booking | None |
| POST | /booking | Create a booking | body: `firstname`, `lastname`, `totalprice`, `depositpaid`, `bookingdates` (`checkin`, `checkout`), `additionalneeds` | `{"bookingid": int, "booking": Booking}` | None |
| PUT | /booking/{id} | Full replace of a booking's fields | path: `id`; body: all Booking fields (required — full replace) | Booking | API Key (see note below) |
| PATCH | /booking/{id} | Partial update — only sent fields change | path: `id`; body: any subset of Booking fields | Booking | API Key (see note below) |
| DELETE | /booking/{id} | Remove a booking | path: `id` | none (status code only) | API Key (see note below) |

**Note on the "API Key" auth classification:** the actual mechanism doesn't cleanly match any single closed-vocabulary option. Two interchangeable methods work for all three write endpoints: (1) a `Cookie: token=<token>` header, where `<token>` comes from `POST /auth` — this is what the official docs lead with; or (2) literal HTTP Basic auth (`Authorization: Basic <base64(username:password)>`), which bypasses `/auth` entirely. Neither is a standard `Authorization: Bearer` header, so "API Key" was chosen as the closest bucket for "a token value attached via a header/cookie, not OAuth2".

**Decision (2026-09-17):** this framework standardizes on the **Cookie-token flow** (`POST /auth` → store token → attach on writes) as its primary auth mechanism — it's the more realistic, transferable pattern (login-once-reuse-everywhere), matching how most real APIs work. Basic auth is kept only as the mechanism for one dedicated negative/auth-bypass test case, not as the main pattern `get-api-auth`/`pytest-api` build fixtures around.

- **Feature summary:** Restful-booker is a free, public demo REST API (by Mark Winteringham) simulating a hotel booking system — login → token → CRUD — built specifically as a practice target for API test automation. Distinct from the same author's separate `restful-booker-platform` project at automationintesting.online (a larger microservices demo) — the two must not be conflated.
- **In scope:** the 8 endpoints listed above; auth via token exchange or Basic auth; full CRUD lifecycle on a booking resource.
- **Out of scope:** no user/account management beyond the single fixed demo credential; no role/permission system; no payment processing (simulated only).
- **Business rules / edge cases:**
  - `RULE-booking-post-open-no-auth`: `POST /booking` requires no authentication — anyone can create a booking, deliberately mirroring a public "reserve a room" action. — affects `POST /booking`
  - `RULE-booking-write-requires-token`: `PUT`/`PATCH`/`DELETE` on `/booking/{id}` require a valid token (via Cookie or Basic auth); an unauthenticated write returns `403 Forbidden` (verified live). — affects `PUT /booking/{id}`, `PATCH /booking/{id}`, `DELETE /booking/{id}`
  - `RULE-booking-delete-status-201`: `DELETE /booking/{id}` returns `201 Created` on success, not `200`/`204` as REST convention might suggest — worth asserting on exactly rather than assuming. — affects `DELETE /booking/{id}`
  - `RULE-booking-put-full-replace`: `PUT` expects every booking field (full replace — omitted fields risk being overwritten); `PATCH` is the safer choice for a single-field update. — affects `PUT /booking/{id}`, `PATCH /booking/{id}`
  - `RULE-auth-dual-mechanism`: Either a `Cookie: token=<token>` header (from `POST /auth`) or HTTP Basic auth (`base64(admin:password123)`) satisfies the write-endpoint auth check — the two are interchangeable; a suite should pick one and stay consistent so failures are easy to attribute. — affects `POST /auth`, `PUT /booking/{id}`, `PATCH /booking/{id}`, `DELETE /booking/{id}`
  - `RULE-auth-no-role-concept`: There is no admin/guest role distinction on this API — wrong-role negative tests don't apply here the way they would on a real multi-role API. — affects auth/authz test design generally
  - `RULE-data-auto-reset-10min`: The shared public instance resets to its seed state (10 pre-loaded bookings) every 10 minutes; anything created or changed can vanish mid-session. Suites must create, verify, and clean up within a single run rather than assuming state persists across runs. — affects all stateful endpoints
  - `RULE-data-shared-instance`: The instance is shared across everyone practicing against it — tests must not assert on exact total booking counts, only on the specific resource id they created. — affects `GET /booking`
  - `RULE-infra-cold-start-latency`: Runs on a free Heroku dyno with occasional cold-start latency on the first call after idle — a generous timeout or one retry on the first request of a run avoids a false failure. — affects test/framework infrastructure (timeout/retry config), not a specific endpoint
  - `RULE-ping-health-check`: `GET /ping` returns `201 Created` with body `Created` — usable as an environment-up smoke check before a run. — affects `GET /ping`

  Negative auth states explicitly called out as easy to script (all expected to return `403` on the write endpoints): no token at all, a malformed token, and Basic auth with a wrong password.
