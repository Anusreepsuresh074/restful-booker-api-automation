# API Authentication

_Generated by get-api-auth on 2026-09-17. Re-run when the API's auth mechanism changes._

## Auth method(s)

| Endpoint group | Method | Notes |
|---|---|---|
| `GET /ping`, `POST /auth`, `GET /booking`, `GET /booking/{id}`, `POST /booking` | None | No `Authorization`/`Cookie` header needed or checked. |
| `PUT /booking/{id}`, `PATCH /booking/{id}`, `DELETE /booking/{id}` | API Key (closest closed-vocab fit — see note) | Two interchangeable mechanisms accepted: (1) `Cookie: token=<token>` obtained from `POST /auth` — **this project's chosen primary mechanism**; (2) `Authorization: Basic <base64(username:password)>`, which bypasses `/auth` entirely — kept only for one negative/bypass test case per project decision recorded in `context/api-context.md`. |

Neither mechanism is a standard `Authorization: Bearer <token>` header — the token is carried as a raw `Cookie` value, and there's no OAuth2 flow, hence "API Key" rather than "Bearer" or "OAuth2".

## Swagger/OpenAPI findings

No OpenAPI/Swagger spec file is reachable as static JSON/YAML — `apidoc/index.html` is a client-rendered SPA (apiDoc tool), and its underlying `api_data.json` data file doesn't include a `securitySchemes`/`securityDefinitions` block (apiDoc doesn't model auth that way). Auth behavior below comes from the apiDoc data file's per-endpoint notes plus the Field Guide document (the *Restful-Booker Field Guide* PDF (a third-party guide, not included in this repo)), whose author states every request/response pair — including the unauthenticated-vs-authenticated `PUT` calls — was exercised live against the running API, not copied from a doc page.

## Auth endpoint(s)

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth` | Token issuance — the only auth endpoint this API exposes. No refresh, no logout/revoke endpoint exists. |

## Request shape

```
POST /auth
Content-Type: application/json

{
  "username": "<username>",
  "password": "<password>"
}
```

- Both fields are required in the body; no headers beyond `Content-Type` are needed.
- This API has exactly one fixed, published demo credential pair (no account creation, no per-user credentials, no separate roles) — the values themselves should still come from config/env (e.g. `AUTH_USERNAME` / `AUTH_PASSWORD` in `.env`, matching this project's existing `.env.example` convention) rather than being hardcoded in test/fixture code, even though they're not secret in the usual sense.

## Response validation

- **Success:** `200 OK` with body `{"token": "<opaque string>"}`. The token is a short opaque string (not a JWT — it doesn't decode as three base64url segments), so there are no claims (`exp`, `sub`, etc.) to inspect; treat it as an opaque session credential.
- **No documented expiry.** Neither the Field Guide nor the apiDoc data mentions a token lifetime or `expires_in` field. Treat the token as valid for the life of a single test run and re-authenticate per run rather than assuming any specific TTL.
- **Failure cases observed/documented:**
  - Calling a write endpoint (`PUT`/`PATCH`/`DELETE` on `/booking/{id}`) with **no** `Cookie`/`Authorization` header at all → `403 Forbidden`.
  - Calling with a **malformed/invalid token** value → `403 Forbidden` (same shape as the no-token case; the API doesn't distinguish "missing" from "invalid" in its response).
  - Basic auth with a **wrong password** → `403 Forbidden`.
  - `POST /auth` itself with a wrong username/password was **not** captured in either source with its exact response shape — flagged under Open questions below rather than assumed.

## Token storage & fixture naming

- Store the token in-memory for the duration of a test session — there's no reason to persist it to disk or a secrets manager given it's a short-lived, non-sensitive demo credential with no documented expiry.
- Recommended fixture, matching this project's existing `conftest.py` convention (session-scoped `config` fixture already established there):
  - `auth_token` — session-scoped fixture that calls `POST /auth` once with credentials from config/env and returns the token string.
  - `auth_cookie_header` (or fold directly into the booking helper's write methods) — a small helper/fixture that turns `auth_token` into the `{"Cookie": "token=<auth_token>"}` header dict every write call attaches.

## Token reuse & negative auth states

- **Reuse strategy:** authenticate once per test session via the `auth_token` fixture; every write test reuses the same cached token rather than re-calling `/auth` per test. No refresh flow exists, so there's nothing to trigger on expiry — if a write call ever returns `403` unexpectedly mid-run, that's a test finding to report (possible session issue), not something to silently retry past.
- **Concurrency:** if tests run in parallel (`pytest-xdist` is already a project dependency), share one token per worker process rather than having every parallel test re-authenticate independently — a session-scoped fixture per `pytest-xdist` worker achieves this.
- **Negative auth states needed by `api-test-design`'s auth-authz cases:**

  | State | How to obtain it |
  |---|---|
  | Missing/empty token | Omit the `Cookie`/`Authorization` header entirely on the write call. |
  | Invalid/malformed token | Take a real token from `auth_token` and mutate it (e.g. truncate or flip a character) — never fabricate an unrelated-looking string, and never reuse a real revoked token since none can be revoked on this API. |
  | Expired token | **Not obtainable** — no documented expiry, no refresh/short-TTL override exists on this API. Flagged under Open questions; do not fabricate an "expired token" fixture. |
  | Wrong-role / insufficient-scope token | **Not applicable** — this API has no role/permission concept (single fixed demo account, no admin vs. guest distinction), confirmed in `context/api-context.md`'s `RULE-auth-no-role-concept`. |
  | Permission/plan-scoped denial variants | **Not applicable** — no org/branch/permission/plan concept exists on this API at all. |
  | Basic auth, wrong password | Base64-encode `admin:<wrong password>` and send as `Authorization: Basic <...>` — this project's one designated Basic-auth test case. |

## Open questions / follow-ups

- `POST /auth` with wrong/missing credentials: neither source captured the exact response status/shape for this case (only the write-endpoint 403 behavior is documented). `pytest-api` will need to make one live call to observe this before asserting on it exactly — flagging rather than assuming it's also a plain `403` or `200` with an error body.
- No way exists to obtain a genuinely expired token on this API (no TTL, no refresh, no override) — any "expired token" test case in `api-test-design`'s matrix should be dropped or explicitly marked as not applicable to this API, rather than simulated.
- Wrong-role and permission/plan-scoped negative states don't apply to this API at all (no roles, no orgs, no plans) — `api-test-design` should not generate those case types for auth-authz coverage here.
