## Open questions / follow-ups

- **Row 4** (`POST /auth` wrong credentials) and **Row 5** (missing `password` field): expected status/body is unconfirmed in both `context/api-context.md` and `context/api-auth.md`. `pytest-api` (or a human) needs one live call against each before the row can assert an exact status/body — do not assume `403`/`400` without checking.
- **Row 9** (`GET /booking` filter with no matches) and **Row 19** (`PUT` with a partial body): tagged `[Assumption]` — plausible inferred behavior, not a documented rule. Needs live confirmation before the expected result is treated as fact.
- **`GET /booking/{id}` with a nonexistent id** and **`DELETE /booking/{id}` on an already-deleted/nonexistent id** — no rule in `context/api-context.md` documents expected behavior for either case, so no row was generated for them (per this skill's no-fabrication guardrail, not an oversight). Flagging as `needs get-context re-run — no business-rule signal`, or a one-off live call to observe and document the real behavior before adding these as cases.
- **`POST /booking` body-level field validation** (e.g. missing `totalprice`, wrong `bookingdates` types, non-boolean `depositpaid`) — `context/api-context.md` documents the happy-path payload shape but no validation-rejection rule for malformed bodies. No negative/boundary rows were generated for this to avoid fabricating a status code. Same `needs get-context re-run` flag applies — there's no local source repo for this third-party API to mine further, so this would need a live-exploration pass.
- **Basic-auth-wrong-password (Row 18) is implemented once, on `PUT` only** — not tripled across `PUT`/`PATCH`/`DELETE` — per the project's decision (recorded in `context/api-context.md`) to reserve Basic auth for a single dedicated negative case rather than the primary auth pattern. Not a gap.
- **No expired-token case** was generated — `context/api-auth.md` confirms this API has no token TTL or refresh mechanism, so an expired-token state can't be obtained.
- **No wrong-role or permission/plan-scoped auth-authz cases** were generated — `context/api-auth.md` confirms this API has no role/org/plan concept at all.
- **`RULE-data-auto-reset-10min`** (10-minute shared-instance reset) and **`RULE-infra-cold-start-latency`** (Heroku free-dyno cold start) are cross-cutting suite-design/config concerns, not individual endpoint test cases — `pytest-api` should apply them as: every test creates, verifies, and cleans up its own data within a single run (never depends on state from a prior run), and the HTTP client uses a generous timeout with one retry on the first request of a run.
- No exact duplicates were found or removed during derivation (no two candidate rows matched on endpoint + rule + case type + input condition + expected result).
